# dsh-moongate v0.8.0

Removes two zero-use paths and keeps the rest, based on 10 weeks of real audit data.

## Shadow rule suggestions (removed)

Shadow mode records "would auto-approve" candidates. A second stage used to group those candidates and offer a one-click "创建规则" button. Over 10 weeks (`~/.dsh/auto-approve/`, 2026-09-05 → 2026-11-20):

- 289 `shadow-candidate` events were recorded, **all** on a single day (2026-11-14, when Shadow was briefly on).
- **0** candidates ever became an allow rule; no rule in `allowlist.json` has the `shadow-suggestion` source.
- The grouping key includes `cwd`/`commandPattern`/`category`, but **0 of 289** candidates carry a `commandPattern` or a `cwd`, so those key parts are always empty and 262 distinct commands collapsed into one bucket.
- Replaying the removed `aggregateShadowSuggestions()` (as of `8e5c5b1`) over the production `events.jsonl` yields exactly **1** suggestion — `{tool:'bash', mode:'danger-full-access', contains:'domain/www'}` — because `extractOperationFingerprint()` treats the `domain/www` fragment of one justification as a path. That is a meaningless suggestion, not a usable rule; combined with 0 adoptions in 10 weeks, the chain is removed.

Removed: `aggregateShadowSuggestions()`, the `shadow-suggestion` rule source, `GET /api/auto-approve/shadow-suggestions`, and the candidate/suggestion list in **审批 → 设置 → Shadow**.

Kept: Shadow mode itself, `wouldPath` recording, and per-project statistics for historical `shadow-candidate` events.

## Stop-loss observation → audit-only debug log (downgraded)

The `guard` switch recorded a `guard-candidate` event on every approval (84 events on 2026-11-18/19/20). Nothing consumed them:

- `aggregateProjectStats()` explicitly skips `guard-candidate`.
- Decision mixes, auto-approve rates and the counters API all exclude them.
- The only consumer was a display row in the Records view — and the mode never changed an approval outcome by design.

`guard` is now a debug log: every approval appends one line to `audit.log` and nothing to `events.jsonl`:

```
GUARD   <tool> mode=<mode> repeat=<n> total=<n> files=<n> sig=<masked signature>
```

`sig` is the operation signature that `repeat` counts, with the home directory folded to `~` and the tool/mode prefix dropped; for file operations it lists the normalized paths, for command operations it carries the masked command text. Without it the line could not answer "which operation is repeating".

Kept: the `guard` config switch, the signature/repeat/file-count bookkeeping (scratch dirs still excluded), and the Records filter for historical `guard-candidate` events.

## Kept, now covered by regression tests

`PROMOTE` (cross-session promotion), `SELFLEARN-CAP` (self-learned rule cap) and `ESCALATE` (reject escalation) are all reachable in code, but produced **0** triggers in 10 weeks: `PROMOTE` 0 / `PROMOTE-SKIP` 0, `SELFLEARN-CAP` 0, `ESCALATE` 0. There were 0 manual rejections in the whole log, so the escalation counters had no input; promotion needs 2–3 sessions confirming the same fingerprint and neutral approvals are a minority (80 of 592).

Deleting reachable-but-unused safety paths is riskier than keeping them, so they stay and `scripts/smoke.mjs` now pins their semantics:

- three consecutive rejections in one session → `escalate` event, `ESCALATE` audit line, counters API reports consecutive/total and limits, `counters-reset` clears them;
- the same fingerprint approved in 2 sessions (with an explicit user-intent phrase) → one `learned` allow rule;
- self-learning at the rule cap → `SELFLEARN-CAP` audit line and no new `self-learned` rule.

## Data note

No migration. `allowlist.json` fields (`guard`, `shadow`, `promotionSessions`, `graduation*`, `selfLearn*`, `denyEscalate*`) and legacy rule `source` values (including the removed `shadow-suggestion`) are read unchanged; existing rules are **not** deleted. Historical `shadow-candidate` and `guard-candidate` records in `events.jsonl` remain readable; `shadow-candidate` still feeds per-project stats, while `guard-candidate` events are explicitly excluded from decision counts (smoke pins this), and the old Records display for both kinds is untouched.

The protected core is unchanged: deny keywords, hard categories, `audit`, self-learning (including the v0.7.2 signature-width gate), session memory, trust roots / project trust, and "remember this action".

## Upgrade

Update the plugin and **restart dsh web** — the host module changed. No configuration change is required; if you had enabled the stop-loss switch it keeps working, now writing `GUARD` lines to `audit.log` instead of events.
